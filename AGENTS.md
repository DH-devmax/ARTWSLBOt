# Project Rules

Canonical repository: `https://github.com/DH-devmax/ARTWSLBOt.git`.
Read `docs/architecture.md` before changing ownership boundaries.

- Production deployment is Docker Compose only. Do not add host service startup,
  SSH installers, a second deployment path, or a Python production chat runtime.
- Docker frontend HMR refreshes mounted product frontend sources only; it is not
  a backend deploy, migration, protocol activation or native acceptance.
  Dependency/lockfile edits require rebuilding the development web image.
  Backend reloads require reviewed schema compatibility and unresolved operations.
  Owner standing authorization (2026-10-29): after a completed change passes its
  required checks, synchronize it to the existing local Compose deployment and
  restart only affected services without asking for another routine restart
  window. This includes a brief API/native connection interruption when needed.
  Preserve the selected release/development mode, local resource limits,
  credentials and immediately previous running release for rollback.
  This is delivery after verification, not a watcher restarting on every edit.
  Frontend-only HMR never restarts API/native connections. Block and report
  unresolved submissions or failed checks; separately confirm destructive data
  removal, incompatible migrations and a new deployment target. Native acceptance
  follows the owner-directed scope and delegation below.
  Never raise readiness merely because a deployment or HMR succeeds.
- Live UI is `web/src/wsl`, using Art Design Pro / Vue / Element Plus.
  Do not expose the imported framework demo routes or embed upstream UIs.
  Product type checks use `web/tsconfig.wsl.json`; clean builds must not depend
  on ignored auto-import declarations generated by running framework demos.
- Feature-management UI baseline: catalogs show saved state read-only; feature
  switches, fields and business operations open in scoped Element Plus dialogs.
  Each editor saves only its selected feature with the current version fence.
  Retain unsaved drafts by actor/platform/account/group, preserve conflicts and
  late-response isolation, and keep dialogs usable on mobile with visible
  actions. Closing or viewing a dialog never submits changes or activates native
  execution. Unimplemented capabilities remain read-only, without fake controls.
- Native and business inventory is owned by `internal/features`. When adding or
  changing a capability, sub-item, business dependency or acceptance result,
  update its platform-specific definition and evidence, run
  `go run ./tools/feature_catalog -write`, and pass the catalog synchronization
  test. Keep native primitives separate from business modules; preserve old
  capability IDs and grants, and never inherit another sub-item/platform's
  acceptance. Generated `docs/feature-catalog.md` replaces hand-counted totals.
- `internal/heatbot` is the Go replacement for MaiBot chat behavior.
  It may propose text only; it must not import native transport, control,
  financial code, database drivers, host commands, or plugin execution.
- All native actions are owned by Go control and must revalidate tenant, group,
  account, package, epoch, current role and deadline at submission.
- Owner-directed local acceptance authorization (2026-10-30): when the owner
  requests testing with already authenticated, owner-controlled accounts in a
  named isolated group, proceed with directory/member/identity reads, existing
  receive-connection enable/resume, prerequisite repairs and bounded testing.
  Resolve the group name to one native group; ask only if it is ambiguous.
  Prefer the existing verified owner/admin as executor and another authenticated
  owner-controlled account, proven to be a current ordinary member, as target.
  For an otherwise unspecified first moderation round, use member mute for one
  minute followed by unmute, one window of at most 300 seconds and a total budget
  of two mutation attempts. Announce the concrete scope before execution.
  If no eligible owned target exists, ask for that missing scope; do not choose
  another person's account. Failed attempts consume budget; do not replenish
  budget or renew windows to exceed the authorized round.
- The owner's conversation instruction/delegation is human authorization.
  The development agent may materialize that scope as an audited superadmin
  grant through the existing administrative UI/API/CLI; the owner need not
  manually click each setup step. Do not repeatedly ask for the same permission
  or identifiers already verifiable from the authenticated account and roster.
  Ask again only for a material scope expansion, destructive/financial effects,
  new signup/SMS/business login, or an unresolved identity/authorization choice.
  Routine fixes, checks, scoped preparation and verified local delivery continue
  autonomously. Repair contradictory implementation gates with reviewed code
  and appropriate tests; preserve the production acceptance gates.
- Owner decision (2026-11-01): a new explicit `native_debug` isolated grant may
  exercise implemented durable Tools without enabling commercial subscriptions
  or production group modules. Existing grants retain `package` admission.
  Debug grants still require an active tenant/group binding, authenticated
  account, current native role, epoch, action/target, deadline and attempt budget.
  This is not a grant to assistants or production workers. Unsupported actions
  stay unavailable. Administrator grant/revoke requires the native owner.
- Controlled acceptance Tools are a separate superadmin surface with explicit,
  persisted account/group/target/action/deadline/budget grants, including grants
  materialized under the owner's delegation above. Every submission must still
  satisfy its persisted admission mode (package checks for `package`), group
  binding, current role, account epoch and deadline.
  Never manufacture authorization or role evidence with direct SQL, disable
  validation, or infer tenant ownership from a native roster. This development
  delegation grants no new capability to the product assistant or heatbot:
  never add grant creation, arbitrary HTTP/Shell/SQL or native execution to their
  tools. Unknown submissions are queried/reconciled, never replayed.
  See `docs/controlled-tools.md`; synthetic tests do not authorize real effects.
- Workspace switching is a view operation. Platform (`wsl` / `lajiaoliao`)
  and purpose (`management` / `chat`) are separate immutable account scope.
  Each purpose pool shares 10 accounts across platforms, at most 30 bindings
  per account. There are at most 300 management groups and chat covers only
  those same authorized groups. Native identity is unique per platform;
  never duplicate an identity/connection owner.
- MaiBot workspace is superadmin-only. Normal tenant permissions remain the
  intersection of explicit grants, package, group authorization and native role.
- No empty scope fallback or cross-group learning, memory, cache or attachment.
  Credentials stay sealed; never return or audit API keys, prompts or passwords.
- Applied migrations are immutable; add a forward migration. Never reset `wsl`.
  Database integration tests may rebuild only `wsl_test`, serially.
- Monitoring is project-only: API/heatbot read their own process and cgroup;
  PostgreSQL statistics are restricted to the current business database and Web
  is reachability-only. No Simon service, host root/PID, Docker socket,
  process enumeration, environment/command-line reads or arbitrary proxy routes.
- `native_ready` and `ai_ready` remain false until their documented acceptance
  criteria pass. Saved configuration is not runtime activation.
- Run architecture checks, Go race/sodium tests, isolated PostgreSQL tests,
  frontend build and container smoke before release. Record real results in
  `docs/test-report.md`; do not describe targets as measurements.
- Automated regression tests use synthetic protocol fixtures and never sign up,
  send SMS, log in or operate real groups. Owner-directed isolated acceptance is
  a separate explicit run under the delegation and persisted grants above.
  Documentation edits alone do not activate native execution or raise readiness.
- New engine capabilities need scope/concurrency/cancellation tests and an
  updated entry in `docs/maibot-migration.md`. Unadapted plugins stay disabled.
- `internal/assistant` is dual-platform, single-group bounded orchestration with no trusted identity,
  database/native/financial/host/plugin access. Tools are whitelist-only.
  Model output cannot apply changes; explicit human approval uses the shared
  control configuration transaction or separately admitted durable native action.
  Group action permissions are explicit and never inherit manager. The assistant
  cannot use controlled-test grants or native_debug; per-platform production
  admission remains independent of implementation and controlled acceptance.
  Missing model usage retains its reservation; no paid automatic retries.
- Eino v0.9.22 belongs only in `internal/assistantadapter`: three model calls,
  six sequential tools and a 90-second deadline. Core assistant and aigateway
  packages remain standard-library-only. AI models cannot apply configurations.
- Both AI consumers use the control-owned shared gateway, sealed business keys
  and immutable rate snapshots. Never reuse architecture-analysis credentials.
  Heatbot receives a single-use scoped grant, alias and version, not vendor keys.
  Submitted unknown usage stays frozen; corrections append to the credit ledger.
- Tenant roles never imply group access for non-owners. Every restricted tenant
  transaction sets the authenticated website actor. Access changes revoke website
  sessions and pending work; owners are explicitly confirmed, never inferred.
  Commercial PLUS/PRO periods last exactly 720 hours; early renewal does not
  issue early credits, and legacy token balances are never converted.
- Architecture maintenance: run `python tools/architecture/architecture.py update`
  after structural code changes, then `check` and the existing architecture guard.
  Run the approved CodeBoarding incremental analysis when its trusted baseline
  exists; never silently replace a failed incremental run with full analysis.
  Update only affected Mermaid views under `docs/architecture/generated`.
  Every dependency must cite code evidence. Preserve `docs/architecture.md` and
  human decisions; report contradictions instead of rewriting them automatically.
  Never send runtime data or secrets to the architecture model, and never load
  analysis caches produced by an untrusted PR. See `docs/architecture/README.md`.
- Architecture triggers: imports/entry points update module views; Compose or
  proxy changes update system view; agent tools, authorization or approval
  wiring update agent/business views. A source-line-only change updates evidence,
  not diagram layout. Run the tooling tests and Mermaid renderer after changes.
- CodeBoarding preflight must match repository, ref, runner settings and ancestor
  commit. Missing/incompatible baselines block analysis with a fresh report.
  Preserve old caches; do not initialize, relabel or restore an unrelated baseline
  to hide failure. Full initialization and source disclosure need owner approval.
  Diagram-only extraction changes must not invalidate the model namespace.
  Successful analyses keep a private durable checkpoint outside disposable cache;
  only an intact checkpoint with exactly matching provenance may recover a missing
  active baseline automatically. Check artifact integrity before loading upstream
  serialized state, and never silently fall back from incremental to full.
- Report code-fact checks, advisory model analysis, CI execution and production
  acceptance separately. Do not cite an old success or another worktree's graph
  as evidence for the current revision.
