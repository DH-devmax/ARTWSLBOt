# 原生登录网络排查

日期：2026-10-26，时区 Asia/Shanghai。

## 本次问题

滑块先失败、随后通过时，前端没有清除之前的「人机验证未通过」，
导致该提示遮住后端返回的网络错误。现在成功的验证码回调和成功轮询会清除旧提示，
重复或关闭后的验证码回调不能再次提交。

原有客户端把所有 HTTP transport 错误归为「请求结果未知」，包括连接前的 DNS 安全拦截。
当前本机容器将官方域名解析为 `198.18.0.0/15` 中的代理映射地址，
该范围被公网地址策略拦截。旧事务未保留底层错误，因此不能据此认定旧请求已被上游拒绝。

使用相同的 Go HTTP 客户端，仅对配置中的官方域名首页做 HEAD：

- 不启用加密 DNS 回退：`native_dns_fake_ip`，未建立原生连接。
- 启用回退：解析到公网地址，TLS 校验通过，首页返回 HTTP 404。

404 只证明这条网络路径可用，不代表注册、短信、登录或 IM 凭据验收通过。
本次排查没有重放真实登录、发送短信或提交注册。

## Docker 设置

默认保持系统 DNS 和公网地址校验。使用 fake-IP 代理的部署可在 `.env` 设置：

```dotenv
NATIVE_DNS_OVER_HTTPS=true
```

随后通过既有 Docker Compose 部署流程重建/更新 API。该设置只传入 API。
本机开发部署已启用，常规部署默认关闭。

回退仅在系统返回的所有地址都位于 `198.18.0.0/15` 时执行；
向固定 `https://1.1.1.1/dns-query` 查询该域名的 IPv4 地址。
查询不携带账号、密码、验证码、原生请求头或令牌，但解析提供方可以看到域名。
结果必须是公网地址，再将已验证的 IP 交给拨号器，TLS 仍校验原始业务域名。
不跟随重定向、不使用环境代理、不直接连接 fake-IP，也不放行私网或云元数据地址。
公共 IPv4 解析失败时停止请求，不回退到 HTTP 或关闭证书验证。
IPv6-only 部署应修正系统 DNS；此加密回退目前只提供 IPv4。

解析调用最多 5 秒、响应最多 16 KiB，不缓存超过本次连接的地址。
业务请求仍保持账号串行、原有超时和不自动重试策略。

## 状态含义

| 状态或错误 | 含义 |
| --- | --- |
| `native_dns_fake_ip` | 服务端收到代理映射地址，且未启用回退；原生请求未发出 |
| `native_dns_failed` | 系统解析失败；原生请求未发出 |
| `native_dns_fallback_failed` | 加密解析未取得可用公网地址；原生请求未发出 |
| `native_origin_rejected` | 目标地址未通过公网策略；原生请求未发出 |
| `native_transport_unknown` | 连接未正常完成，无法确认上游处理结果；不得自动重试 |
| `native_response_invalid` | 已收到无法核验的回包；不得自动重试 |

界面只显示限定的诊断类别（超时、提前断线、连接未完成）及已有上游返回码，
不返回底层错误、完整 URL、密码或验证码。开户持久屏障仍区分「未发送」
和「已经提交但结果未知」，未知结果不得因网络修复而直接解锁。

用户核对官方客户端状态后，可刷新 WebUI，重新打开注册/登录并手动开始新的验证。
本次变更不会自动恢复旧验证码或重放旧请求。
